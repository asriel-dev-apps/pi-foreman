# ADR 0001: jev によるタスク・ルーティング層 (pi-foreman)

- Status: Accepted
- Date: 2026-09-22
- Scope: pi 拡張 1 本。claude / codex への展開は本 ADR の対象外

## 背景

着手前に決まっていないと後で高くつく判断が毎回ある。サブエージェントに委譲するか、
どのモデルで実装するか、どの skill を読むか、レビュー (rv) を回すか、HTML 進捗レポートを
書くか。いまはこれらを毎回その場の勘で決めており、規模の小さいタスクに重い手順を掛けたり、
逆に危ない変更をレビューなしで通したりする。

TypeSafe の jev は、テキスト 1 本 (state) に対して型付きの質問を投げると、確率つきの答えを
返す判定モデルである。散文を書かないので、返ってくるのは分岐できる数値だけ。

実測 (2026-09-22, `jev-1.13.0`, 4 問同時 1 リクエスト):

| state | size (0-3) | risky | visual | delegable | 所要 |
|---|---|---|---|---|---|
| README の typo を直して | 0.00 | 0.04 | 0.84 | 0.75 | 0.58s |
| 認証トークンの二重リフレッシュを直して。決済 API も呼ぶ経路 | 1.31 | 0.87 | 0.14 | 0.25 | 0.61s |
| TUI の設定画面を追加、キーバインド衝突なしで | 1.70 | 0.28 | 0.97 | 0.32 | 0.65s |

risky と visual は生の性質としては当たっている。typo に visual 0.84 が出たのは質問文の欠陥で、
これは後述の決定 4 で扱う。

## 決定

### 1. 判定は「生の性質」だけを jev に問い、手順への写像は自前のルール表で持つ

jev に問うのは、どの開発環境でも意味が通る性質に限る。

| key | type | 問う内容 |
|---|---|---|
| `size` | score (4段) | 一行修正 / 小さな自己完結した変更 / 複数ファイルの機能 / アーキテクチャ級 |
| `risky` | noul | 間違えるとデータ喪失・秘密漏洩・本番破壊など取り返しがつかないか |
| `visual` | noul | 実行して初めて見える UI/TUI 画面を変えるか (決定 4 で語を確定) |
| `delegable` | noul | 短い書面のブリーフだけで別エージェントに渡せるか |
| `kind` | choice | docs / security / ui / refactor / infra / research / other |

「rv を回す」「HTML レポートを出す」「html-doc skill を読む」はこの家のルールであって、
jev が学習した概念ではない。したがって choice の選択肢に家のルールを書かない。
`kind` → skill 名の対応は `src/rules.ts` の表で持つ。

この形を採る理由は 3 つある。複数質問が 1 往復で返るので分割しても遅くならない (実測 0.6 秒)。
確率が返るので、誤発火した項目だけ閾値を上げて直せる。そして 60 個を超える skill の
description を `criteria` に流し込むと、pi が持たない skill 台帳に質問定義が結合する。

### 2. 判定結果は助言として注入する。強制はしない

pi の `before_agent_start` は `event.prompt` を受け取り、セッションに残るメッセージの注入と
システムプロンプトの差し替えを返せる。ここに「このタスクは中規模・取り返しがつきにくい・
rv を回してから受け入れること」といった一段落を注入する。

実際に rv や HTML レポートに相当する処理を pi 側で起動はしない。pi には claude 側の
review skill / html-doc skill にあたる資産がないため、文面として書くところまでが本拡張の責務。

節目の再判定は `agent_settled` (pi が自動継続しないと確定した時点) で行う。

### 3. state はユーザーのプロンプトとリポジトリ概要

`event.prompt` に、cwd のリポジトリ名・`AGENTS.md` の `Tier:` 行・`git status` の要約
(変更ファイル数と拡張子の内訳) を数行足したものを state とする。プロンプト文だけでは
規模が読めない依頼 ("このバグ直して") が実際にあるため。

### 4. `visual` の質問文は「走らせないと見えない画面」に限定する

実測の `README の typo` → `visual 0.84` は誤発火である。repo 概要を state に足しても直らない。
README が画面に数えられるかは、リポジトリの要約には書かれていないからである。
質問文を *"a UI or TUI that must be run to be seen"* の線で書き直し、typo の例を負例として
フィクスチャに入れる。

**質問文と閾値がこのプロジェクトの成果物本体であり、拡張のコードは配線にすぎない。**
よって質問定義・閾値・ルール表は `src/questions.ts` / `src/rules.ts` に置き、
`@earendil-works/pi-coding-agent` に依存させない。拡張はそれを呼ぶだけの薄い層とする。

### 5. すべての異常系は fail open

キー欠落・タイムアウト・429・壊れたレスポンスでは判定を出さず、エージェントはそのまま進む。
エラー報告は毎分 1 回まで。助言専用の層が、死んだエンドポイントのためにターンを止めてはならない。

### 6. 置き場所は新規リポジトリ `asriel-dev-apps/pi-foreman`

既存の `pi-orchestrator` は寿命も機構も別物なので相乗りさせない。

## 検証方法 (DoD)

検証の主軸は **フィクスチャ** (`tests/fixtures.json`) である。質問文がこのプロジェクトの
成果物本体なので、質問文を触ったら `scripts/fixtures-check.ts` を回し、意図した向きに
スコアが動くことを確かめる。誤発火を見つけたら、それを負例としてフィクスチャに足す。

バックテスト (`scripts/backtest.ts`) は補助である。`~/.claude/projects/*/*.jsonl` から
冒頭のユーザープロンプトを入力、そのセッションでの `Agent` 呼び出し・`Skill` 呼び出し・
`project-docs/*/reports/*.html` への `Write` を正解ラベルとして突き合わせる。

**バックテストの数字を一致率として読んではならない。** 理由は 2 つある。

1. ラベルは「数時間のセッション中に一度でも委譲したか」であって、冒頭プロンプトから
   予測できる性質ではない。冒頭が予測できてしまうとしたら、それは当てずっぽうである。
2. 着手前ルーティングの対象になる冒頭プロンプト、すなわち仕事が書かれている冒頭は、
   実際のログでは少数派である (実測: 153 セッション中 6 件。残りは継続の合図、起こされた
   だけの通知、`/security-review` のような定型コマンド)。標本が小さすぎる。

バックテストの使い道は、割合ではなく **個々の食い違いを読むこと** にある。実際これで
`visual` と `delegable` の質問文の欠陥が 1 件ずつ見つかり、どちらもフィクスチャに変換した。

モデル選択は検証の対象外とする。メインセッションのモデルはメタデータから取れるが、それは
「そのとき選ばれていた設定」であって、タスクに対する判断の記録ではないため。

## 運用上の前提

API キーは環境変数 `TYPESAFE_API_KEY` からのみ読む。追跡ファイルに書かない。
現行キーはローテーション予定である。バックテストの抽出器は、読み込んだ state を標準出力に
出さないこと (走査対象のログ自身にキーが含まれ得るため)。
